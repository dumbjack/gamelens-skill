# 图片归档与复用规范

## 归档时机与目录

按 [本次任务规格](task-adaptation.md) 决定采哪些图片。采样时保存完整原帧，产生 ROI 时同时写入父图关系和来源。报告生成前完成索引及视觉核对，之后从索引生成报告。证据文件的来源结构通用，具体游戏字段和图片选择规则可以扩展。

以下为新任务的推荐布局；已有归档可以保留其目录和等价字段，不必为改名重做取证：

```text
Trace_Evidence_Pack/
  source_manifest.json
  image_index.json
  asset_links.json
  frames/                 # 完整原帧
  crops/                  # 从原帧导出的任务所需局部
  reference_images/       # 模板或其他参考来源
  tool_calls.jsonl
  reports/                # 按用户要求生成
```

独立图片、来源索引和业务关联是必要内容；文件名和拆分方式可以适配现有项目。无需保存视频每一帧，但所有纳入分析、引用或复用索引的原帧与派生图都应保留。

## 1. 图片本体

- 完整原帧指未裁剪的画面；原生分辨率是另一项属性，分别记录，不能把放大后的图称为原生高清。
- 新采集的父原帧保留原生尺寸，不加框、不加字、不缩小。对 HUD 等细节优先采用无损编码。已有 JPEG 保持原文件，转换为 PNG 不会恢复丢失的细节。
- 裁剪优先由已存父原帧生成。若需从视频重新解码，核对实际帧号，保存同帧完整画面并关联，不能将附近时间的原帧当作同帧父图。
- 缩略图、拼图和标注图是派生用途。另存文件和派生关系，不覆盖原帧或裁剪图。
- 用来源 + 实际帧号 + ROI/变换识别已有素材，优先复用。证据 ID 在一次归档内唯一；跨任务使用 `archive_id + evidence_id`，避免各包中的 `E0001` 冲突。

### GameLens 当前本地接口的注意点

使用本地 `gamelens.vision.capture` / `investigate` 时先核对当前源码。此次使用的版本中：

- `region` 是相对于原视频完整帧的归一化空间坐标 `[x1, y1, x2, y2]`，原点在左上角；不是时间区间。
- `capture` 的 `max_width` 默认 960，可能缩小宽视频。归档完整原帧时设置不小于源宽度的值，并检查输出实际尺寸；已有缩小图应如实记录。
- `capture` 的返回 `file` 固定形如 `frames/E....jpg`，即使传入另一输出目录。写索引前按实际文件位置规范化相对路径并验证存在。
- ID 由 `offset` 生成，多批次需防冲突。`investigate` 单次最多返回 6 帧，设置的 `sample_fps` 不保证实际密度；根据返回 `sampling` 记录实际采样。
- 若返回时间只保留毫秒，保存解码帧号更可靠；缺少精确帧号时标明时间精度，不虚构精确值。

## 2. 来源与图片索引

下列字段是一套可用的规范；允许等价结构，但关联链须可解析。

### `source_manifest.json`

| 字段 | 含义 |
| --- | --- |
| `archive_id` | 本次归档的唯一标识 |
| `sources[].source_id` | 视频、参考工作簿等来源的稳定 ID |
| `sources[].kind` | `video`、`reference_workbook` 等 |
| `sources[].name`, `sha256` | 原文件名及内容哈希 |
| `sources[].locator`, `included_in_package` | 原始位置/链接及是否随包提供 |
| 视频元数据 | 宽、高、fps、时长；必要时说明可变帧率及时间基准 |

### `image_index.json` 的每条图片记录

| 字段 | 含义 |
| --- | --- |
| `evidence_id`, `image_kind` | 唯一 ID；`full_frame`、`crop`、`reference` 或其他派生类型 |
| `source_id`, `file`, `sha256` | 来源、包内相对路径和图片哈希 |
| `width`, `height` | 实际图片尺寸 |
| `timestamp_seconds`, `frame_index` | 视频实际时间和解码帧号；参考图片不适用时用 null |
| `parent_evidence_id` | 裁剪/标注等派生图的父图；原帧为 null |
| `region`, `coordinate_space` | ROI 与坐标约定；未裁剪用 null，参考嵌图无视频 ROI |
| `region_pixels` | 在原始完整帧上的像素边界，记录取整后的实际范围 |
| `extraction` | 工具、请求时间与实际时间、缩放/变换、调用记录 ID |
| `reference_locator` | 参考嵌图的工作表及锚点行列，必要时含图片序号 |
| `revision_of`, `revision_reason` | 新裁剪或新版本对应的旧 ID 及原因；不适用为 null |

对矩形 ROI 写明 `[x1,y1,x2,y2]` 的右/下边界不包含在内，并验证 `0 <= x1 < x2 <= 1`、`0 <= y1 < y2 <= 1`。如果在缩放图或已有裁剪上圈选，换算回完整原帧坐标后保存；不能混用坐标系。

新记录应在采集时写入上述信息。迁移旧记录时可从采样请求、工具日志和原索引补齐；无法恢复的信息明确标为未知并记录限制，不能凭空补值。

## 3. 业务关联与名称确认

`asset_links.json` 维护图片和业务对象的多对多关联。每条关联至少能表达：

- `evidence_id`、`entity_id`、`entity_type`：图片关联的业务对象，如卡牌、建筑、技能、界面、布局或事件。类型按当前任务扩展，不是固定枚举。
- `unit_type`、`unit_id`：本次拆解单位与 ID；例如回合、操作步骤、关卡、阶段。关卡任务可保留 `level_id`、`attempt_id` 等具体字段；其他任务无需虚设关卡或尝试。
- `requirement_id`、`role`：对应的用户图片要求与观察角色，如升级前、命中时、回合结算或参考图；角色按任务扩展。
- `sequence_id`、`sequence_order`：过程或前后对照图片的有序关系；单图不适用时省略或为 null。
- 适用时记录 `observed_label`、`canonical_name`、`name_status`、`name_evidence_ids`：可见文字、对照名、确认状态及其依据。
- 适用时记录 `presence_status`：`observed`、`reference_only`、`unverified` 等；未观察到不等于不存在。
- 适用时记录 `action_status`：`offered`、`used`、`purchased` 或任务自定义状态；出现购买入口不等于已经购买。
- `observation`、`interpretation`、`limitations`：直接观察、解释及限制分别记录。

名称状态可用 `confirmed`、`appearance_match`、`unconfirmed`。`confirmed` 应有游戏内文字或可核对的官方来源；只能确认外观时保留对照名称并标记 `appearance_match`，不要自动认定机制相同。

同一对象在多个拆解单位中出现时复用稳定对象 ID，每次出现独立关联到对应单位与证据。跨游戏的同名物体先核对来源与身份，不能直接合并。模板中的引入位置不能直接复制为当前游戏的首次出现；仅覆盖一段录屏时写“本录屏最早观察到”。

## 修订、再利用与验收

1. 后续任务先按来源、拆解单位、对象、角色及适用的确认状态检索索引，核对哈希与来源后直接复用；无需从 Excel 解包或从展示页反向抓图。
2. 重新裁剪分配新 ID，关联同帧完整原图并记录 `revision_of`。改名或改变判断时版本化关联记录、注明依据，历史状态保持可追溯。
3. 报告引用归档 ID + 证据 ID。嵌入图片只是方便阅读，不能成为唯一副本；排版调整不能覆盖归档图片。
4. 验收索引引用的每个文件可解码、尺寸与哈希匹配，父图存在且同帧同来源，ROI 坐标有效；业务关联中的证据和对象可解析。
5. 对照原帧及本次图片要求检查裁剪和序列，确认请求对象完整、关键文字可读、阶段与顺序正确。布局任务另检查目标与平台。可先用带 ID 的拼图扫查，疑点回到单张原帧放大核对。
6. 打包后检查压缩包完整性，并解压到临时目录验证相对路径和引用链。原视频未打包时说明回放所需来源；图片复用应不依赖原输出目录的绝对路径。

若对外展示需要省略无关画面，记录省略 ID 和原因，检查被保留的裁剪仍有可访问父图；不要留下断链索引。内部归档和展示包的范围分别说明。
